### Stack Tecnológico y Estilos
- Framework: Angular (usa componentes Standalone y la sintaxis de control de flujo más reciente).
- Tipado: TypeScript estricto. Usa interfaces y tipos para cada entidad de la tienda (Product, CartItem, User, Order). No uses `any`.
- Estilos: HTML semántico y CSS/SCSS. El diseño debe ser mobile-first y responsive.
- UI/Iconos: Integra Google Fonts Material Symbols para la iconografía del carrito, perfiles y menús.
- Imágenes: Configura las etiquetas `<img>` con carga diferida (lazy loading) y texto alternativo descriptivo para SEO y accesibilidad.
- Respeta las clases y metodos que te paso, usa clases abstractas, interfaces , enum.
- Usando JPA y las etiquetas necesarias como @Data @NoArgsConstructor @AllArgsConstructor y las validaciones como @id @email @NotBlank @NotNull @Value cuando lo nesecites
- Para la seguridad usa JWT 
- Spring Security
- Hibernate
- Maven
- base de datos MySQL

### Arquitectura y Patrones
- Divide los componentes en "Smart" (manejan lógica e inyectan servicios) y "Dumb" (solo reciben @Input() y emiten @Output()).
- Mantén la lógica de negocio y las llamadas a la API fuera de los componentes; utiliza Servicios inyectables.
- Para el estado de la aplicación (especialmente el carrito de compras), utiliza programación reactiva con RxJS o Angular Signals.
- Usa patrones GRASP
- Patrones MVC
-Uso DTOs
- Respeta estrictamente la separación de responsabilidades:
  1. Controllers: Solo reciben peticiones HTTP, validan el DTO de entrada y delegan la ejecución al Service. No deben contener lógica de negocio.
  2. Services: Contienen toda la lógica de negocio. Orquestan llamadas a sus propios Repositories o a otros Services.
  3. Repositories: Se encargan exclusivamente del acceso a datos.
- Sigue el patrón de Agregados: Un Service solo debe inyectar Repositories de su propio dominio (ej. `ProductoService` usa `ProductoRepository`, `CategoriaRepository`, etc.). Si necesita datos de otro dominio, debe llamar al Service correspondiente, no al Repository ajeno.

### Reglas Específicas del E-commerce
- Moneda y Precios: Muestra siempre los precios utilizando el `currency` pipe de Angular.
- Precisión Matemática: Al calcular totales del carrito, subestaciones o impuestos, evita errores de coma flotante redondeando a dos decimales de forma segura.
- Botones de Acción: Todo botón crítico (como "Añadir al Carrito" o "Pagar") debe manejar un estado de carga (loading) para evitar doble clic mientras se procesa la petición.
- Los talles y los colores sean numeros o letras (depende como lo ingrese el usuario) tiene que ser en mayuscula antes de guardarlo en la base de datos

### Reglas de Interacción entre Servicios
- Carrito y Stock: El `CarritoService` no descuenta stock ni lo consulta directamente; debe llamar a `ProductoService.validarStock()`.
- Flujo de Pedidos: Al concretar una compra, el `PedidoService` es el orquestador. Debe llamar a `ProductoService.descontarStock()` y a `CarritoService.vaciarCarrito()`.
- Seguridad y Roles: Los endpoints del dashboard (`EstadisticaController`) deben estar protegidos y ser accesibles únicamente para usuarios con el rol ADMIN.

### Patrón de Agregados y Creación de Servicios
- Utilizamos un enfoque basado en Agregados para organizar la lógica de dominio. NO existe una relación 1:1 entre Repositorios y Servicios.
- REGLA ESTRICTA: Está terminantemente prohibido crear Servicios para entidades secundarias. Solo se permite crear un único `Service` (Raíz) por cada Agregado.
- La estructura estricta de Agregados de este proyecto es la siguiente:
  1. Agregado Producto (Raíz: ProductoService): Gestiona de forma centralizada Producto, ProductoVariacion, Categoria, ImagenProducto, Color, Talle y ProductoVisita.
  2. Agregado Pedido (Raíz: PedidoService): Gestiona Pedido y PedidoDetalle.
  3. Agregado Carrito (Raíz: CarritoService): Gestiona Carrito y CarritoItem.
  4. Agregado Usuario (Raíz: UsuarioService): Gestiona Usuario.
- Comportamiento esperado: Si necesitas hacer una consulta sobre un color, un talle o una categoría, debes inyectar el `ColorRepository`, `TalleRepository` o `CategoriaRepository` dentro del `ProductoService`. ¡NUNCA crees un `ColorService`, `TalleService` o `CategoriaService`!
